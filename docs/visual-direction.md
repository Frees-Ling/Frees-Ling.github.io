# 视觉方向：从 FIELD LOG 转向「凛风的私人数字书房」

日期：2026-09-16

状态：**待用户选定方向后实施**

## 一、为什么要转向

用户对 2026-09 完成的 FIELD LOG 视觉给出明确负面反馈：
夸张的字体、大量英文、过度装饰。这与该方向的原始设定直接冲突 ——
它不是执行偏差，而是方向本身不合用户意：

| FIELD LOG 的有意设计 | 用户的实际感受 |
| --- | --- |
| 118px 衬线首屏 `Frees Ling / 凛风` | 夸张的字体 |
| 拉丁导航 INDEX / WORK / NOTES / ARCHIVE / ABOUT | 大量英文 |
| 全大写 mono 眉标（`ALL WRITING · 17 ENTRIES`） | 无意义的英文口号 |
| `31.23° N · 121.47° E`、条目编号 `FL-2607-001` | 过度装饰 |
| signal red 作为第二强调色 | 多种竞争强调色 |
| 直角（`--radius: 0`） | （与新方向冲突） |

**保留什么**：技术架构与全部功能不受影响 —— Astro 7、零框架零 hydration、
Pagefind 检索、内容集合、URL 结构、WEB-008 的列表编排器与栏目数据层、
token 闸门、视觉门禁、无障碍基线。视觉整改是**替换外观层**，不是重建。

## 二、Fuwari 为什么看起来舒服（原理，非组件）

分析对象：`archives/sites/Frees-Blog/`（仓库内留存的 Fuwari 派生源码）
与演示站结构。

1. **全部颜色来自单一 `--hue` 变量。**
   `--primary` `oklch(0.70 0.14 var(--hue))`，`--page-bg` `oklch(0.95 0.01 var(--hue))`。
   没有第二个争夺注意力的强调色 —— 这是「安静」的首要来源。

2. **背景的彩度极低（0.01）。** 不是「蓝色背景」，而是中性色里有一点蓝的暗示。
   大面积色块因此不刺眼。

3. **规律性即平静。** 列表里每一条的形状完全相同：标题、日期、分类、一句话描述、
   字数与阅读时长。眼睛不需要为下一条重新学习模式。

4. **元信息从属。** 日期、标签、字数都在，但字号与对比度都低于标题一档，
   从不与标题竞争。

5. **层次靠留白与极淡的分隔线**（`--line-divider: black(0.08)`），
   阴影只出现在浮动面板上，卡片本身没有阴影。

6. **克制的动效**：`--content-delay: 150ms`，圆角 1rem。

**结论**：舒适感来自「单色相 + 低彩度 + 高度规律 + 元信息从属」，
而不是来自横幅、侧栏、卡片这些具体构件。
因此这些构件**都不必复制** —— 复制它们恰恰会丢掉原理、只留下皮。

## 三、工作量评估：借鉴 vs 迁移模板

| | A. 借鉴设计语言（推荐） | B. 迁移 Fuwari 模板 |
| --- | --- | --- |
| 技术栈 | 保持 Astro 7、零框架、零 hydration | 需降级到 Astro 5，引入 Tailwind 3 + Stylus + Svelte + swup + Iconify |
| 现有资产 | 全部保留（编排器、栏目层、token 闸门、门禁脚本、a11y 基线） | 大部分作废并需重写 |
| 首屏 JS | 0 | swup + Svelte 组件 |
| 检索 | 现有 Pagefind 保持 | 需重新接线 |
| 主题闸门 | `check-tokens.mjs` 继续有效 | Tailwind 原子类使 token 闸门失效 |
| 风险 | 中（纯外观层改动） | 高（依赖、构建、回归三重风险） |
| 与用户第 3 条要求 | 一致 | 冲突（会变成 Fuwari 换色版） |

**结论**：走 A。且用户明确要求「不做换皮 Fuwari」，因此连 A 也不复制其构件，
只采用其原理。

## 四、三个原创方向

三者共享同一套原理（单色相、低彩度、规律性、元信息从属），
但**隐喻、主轴与独特构件完全不同**，不是三套换皮。

---

### 方向一 · 书房 —— 书架与卡片目录

**隐喻**：一间书房。知识不是「卡片网格」，而是**卡片目录**（library card catalog）
里的索引卡 —— 这是图书馆真实存在过的检索工具，有标题行、主题标目、编号与
「参见」（see also）交叉引用。

- **主轴**：检索。搜索框是书房的书目查询台，不是一个附属页面。
- **独特构件**：索引卡。条目以卡片目录的形式呈现，卡上有编号、主题标目、
  关联条目。**「参见」交叉引用由真实的标签重叠计算**，把知识关联做进检索本身，
  而不是另做一个装饰性的关系图。
- **导航**：书架式分区（按主题分架），不是顶部横排标签。
- **阅读模式**：正文单栏（720–780px）+ 页边注，长时间阅读优先。
- **蓝色**：深墨蓝作标题与链接，纸白/微米色作底。
- **摄影**：以「图版」呈现，带编号，像书里的插页。
- **最贴合用户原话**「私人数字书房」。

### 方向二 · 星图 —— 知识地图

**隐喻**：一张海图 / 星图。知识是一组可以互相抵达的点。

- **主轴**：关联。每条笔记都显示由真实标签/来源重叠算出的「邻近条目」。
- **独特构件**：**构建期生成的关系图**（零运行时 JS 的静态 SVG），
  不是装饰性球体或粒子背景 —— 它可点击、可导航、有实际检索价值。
- **导航**：书末索引式（按主题分组），不是顶部标签。
- **阅读模式**：正文 + 始终可见的「当前位置」指示。
- **蓝色**：海图蓝 + 细线稿，纸面偏冷。
- **差异化最强**，也最直接服务「知识关联视图」这一要求。
- **风险**：关系图如果不够有用就会退化成装饰；需要真实数据支撑。

### 方向三 · 长卷 —— 时间轴工作台

**隐喻**：一条持续记录的卷轴 + 一张工作台。

- **主轴**：时间。整个站只有一条时间线，分区是**对时间线的筛选**，而非并列的页面。
- **独特构件**：顶部状态条 —— 此刻在做什么（AI 协作、长期记忆、实验），
  来自真实数据而非口号。
- **导航**：筛选器（按主题/年份/类型），不是跳转。
- **阅读模式**：技术手册风 —— 编号插图、边注、代码优先。
- **蓝色**：仪器蓝 + 冷灰台面。
- **最适合**把 AI 协作与长期记忆做成可见线索。
- **风险**：单一主轴对「查资料」不如前两者直观。

---

## 五、共同约束（三方向都遵守）

- 中文为界面主语言；英文只保留专有名词（Python、GitHub、FastAPI、LM Studio、Mem0…）。
- 蓝色承担品牌、链接、导航选中与操作反馈；正文以深灰为主。
- 不使用渐变制造质感；阴影克制，层次优先靠间距、排版与细边框。
- 保留键盘焦点可见与文字对比度达标。
- 保留适量的动效与过渡，不追求「全部去掉」。
- 不引入大型 UI 框架或动画库。
- 不复制 Fuwari 的 CSS、组件、图标组合、插画或页面结构。
- 移除姓名与 Logo 后，不应被认作 Fuwari 换色版。

## 六、实施顺序（选定方向后）

1. 设计 token 层重写（单色相 oklch、圆角、分隔线、阴影）
2. 全局排版与中文文案（导航、页脚、列表、按钮）
3. 首页
4. 文章列表与文章详情
5. 每一阶段：构建 + 视觉门禁 + 实际浏览器截图（390 / 1440，双主题）
6. 知识库与 Studio 视觉统一 —— **注意：这两者目前尚不存在实现**（见 ADR-013），
   因此该步骤只能在它们开始实现时同步进行，现在无法「整改」不存在的页面。
