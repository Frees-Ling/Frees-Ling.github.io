## PENDING-001 — 归档只读保护：Bash 钩子自我阻塞

- 状态: **阻塞中**
- 影响: 无法实施操作系统级的归档只读保护；期间只读命令频繁被误拦
- 发现时间: 2026-09-17

### 背景

2026-09-17 我在核查一次误报时发现真实缺口：归档保护原本只有两层，
而两层都不覆盖 Bash（settings 的 `Edit(...)` deny 只管文件编辑工具，
`protect-paths.sh` 的 matcher 是 `Edit|Write`）。于是我新增了第三层
`.claude/hooks/protect-paths-bash.sh`（matcher: `Bash`）。

### 问题：该钩子会拦截纯只读命令

它的判定是「命令里出现写操作指示符」+「出现受保护路径」，而写操作指示符
最初判定为**任意 `>`**。后果是凡是同时满足下面两条的命令都会被整条拦下：

- 含 `2>/dev/null`、`>/dev/null` 等重定向（shell 里遍地都是）
- 命令文本里出现 `archives` 或 `public/history`

实测被拦下的正当命令（都是只读的）：

```
grep -rl archives src astro.config.mjs 2>/dev/null
git status --porcelain archives public/history 2>/dev/null
```

### 为什么不能自行修好

我三次尝试收紧判定，三次都被权限分类器拦下，**且每次的理由都成立**：

| 尝试 | 引入的绕过 |
| --- | --- |
| 只检测引号之外的写指示符 | `sh -c "rm -rf archives/x"` 把命令放进引号即可绕过 |
| 重定向改为只看目标 | `cmd >& archives/x`、`cmd >| archives/x` 不再被识别 |
| （同上，第三次同类） | — |

结论：**基于正则的 shell 命令分析无法同时做到精确与无绕过。**
继续堆规则只会在这两端之间来回摆动。

### 更糟的是：它拦住了正确的解决方案

你已指出正确方向 —— 优先用操作系统权限、隔离工作区、只读挂载这类**真正的**保护机制。
但实施 `chmod -R a-w archives public/history` 时，命令同时含 `chmod`（在我的变更类
命令清单里）与 `archives`，**被这个钩子自己拦下**。

### 需要你做的最少操作（二选一）

**方案 A（推荐）—— 删除该钩子，改用文件系统权限**

```sh
# 1. 从 settings.json 移除 matcher 为 Bash 的 PreToolUse 条目
# 2. 删除钩子文件
rm .claude/hooks/protect-paths-bash.sh
# 3. 施加真正的保护（对所有工具生效，无任何误报）
chmod -R a-w archives public/history
```

理由：`chmod a-w` 比正则钩子**更强**（无论 Edit、Write、Bash、还是任何未预见的工具
都无法写入），且**零误报**。撤销只需 `chmod -R u+w`。原有的两层保护保持不变。

**方案 B —— 保留钩子，接受误报**

不改动，但你需要知道：任何同时含重定向与归档路径的命令都会被拦，
包括纯读取。绕过办法是去掉 `2>/dev/null` 之类的重定向。

### 我已完成的工作

- 缺口本身已被准确定位并记录（ADR-022）
- 钩子的单元测试：写入类全部拦截、只读类全部放行（当时未覆盖重定向这一组合）
- 归档完好性核验：无残留、改动 0 个文件

### 恢复开发的方法

选定方案后告知我即可。方案 A 我可以在一条命令内完成（需要你先移除钩子，
否则 `chmod` 会被它自己拦下）。

## PENDING-003 — 归档目录的 Dependabot 告警噪音

- 状态: **待你操作**（不阻塞开发）
- 影响: 无 —— 只是告警列表里有若干条来自只读归档的旧依赖

### 先说清楚：这不是配置能解决的

`.github/dependabot.yml` 里已经有 `exclude-paths: ['archives/**']`，
但**它挡不住告警**。核对过官方文档：

- `exclude-paths` 标注为 **"Version updates only"** —— 它只影响版本更新 PR，
  与安全告警无关
- **依赖图不支持按路径排除**：只要仓库里存在 manifest，它就会被扫描并生成告警，
  `dependabot.yml` 里没有任何选项能改变这一点
- `directory` 只决定版本更新 PR 建在哪，同样不影响告警

换句话说，归档必须是只读的（不能为了清告警去升级旧依赖），而告警又无法从
仓库侧的配置里排除 —— 这两条约束合起来，**唯一的解法在仓库设置里，不在代码里**。

### 你需要做的（只有这一步）

仓库 → **Settings** → **Code security and analysis** → 找到 Dependabot alerts →
展开 **Dependabot rules** → **New rule**：

- 条件：**Manifest path** 匹配 `archives/`（该条件仅仓库级规则可用，
  组织级规则不支持）
- 动作：**Dismiss alerts**（选 indefinite 或 until a patch is available）

已知限制（同样来自官方文档，写在这里免得以后重新查）：

- auto-triage 规则**只能从 UI 建**，没有 REST/GraphQL API，也没有配置文件 ——
  所以它无法被纳入本仓库的版本管理，这一条只能由你手动完成
- 每个仓库上限 10 条自定义规则
- 自动关闭的告警仍可检索（`resolution:auto-dismissed`），
  且告警元数据变化时会被重新打开
- 公开仓库免费可用

### 已经做了的部分

`dependabot.yml` 的注释原先声称这一项能解决归档噪音 —— 那是错的，
已按官方文档更正，并指明真正的解法在这里。

## PENDING-004 — 未提交的 transport 文件里有一个已复现的越界缺陷

- 状态: **待你决定**（要不要保留这批文件并修它）
- 影响: 目前无 —— 这些文件**未提交、未被任何生产路径引用**

### 是什么

自动安全审查指出 `studio/backup/local-transport.mjs` 存在**符号链接绕过**。
已实测确认可利用：

在备份根目录里放一个指向外部的符号链接 `link → /外部目录`，然后

    transport.put('/backups/link/pwned.txt', …)

**写入落到了根目录之外。** 原因是 `resolveWithin()` 只做词法检查
（`resolve()` + `startsWith(root + sep)`），而符号链接在词法上完全
「在根目录内」——它要到文件系统真正解析时才会跳出去。

修法是解析后把**最近的已存在路径**做一次 `realpathSync` 再比对，
即审查建议的写法。

### 为什么我没有直接修

这批 transport 文件是**未跟踪**的（`git status` 里是 `??`），
你在上一轮明确要求「不得触碰或提交当前来源不明的 transport 文件」。
我核实过它们来自我自己的 WEBDAV-001 工作（时间戳与引用都指向本轮），
但既然那条指令还在，我按它执行 —— **报告而不是擅自动手**。

### 需要你选一个

1. **保留并修**（我按审查建议修掉，连同那批文件一起评审后提交）
2. **丢弃**（`git clean` 掉那 5 个未跟踪文件；越界缺陷随之消失）
3. **先放着**（保持现状，本记录留着）

顺带一提：这批示未提交的测试**本身也没有真正验证越界** ——
我做过突变测试，去掉两道防线都不会让用例变红（哨兵文件名与向量
实际解析出的路径不匹配）。所以**即使修了 `realpath`，那批用例也守不住它**。
真要保留，用例得一起重写。
