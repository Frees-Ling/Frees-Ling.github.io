# Owner 认证威胁模型（SEC-002）

日期：2026-09-17
状态：结论已定，两道防线已实现并有测试
相关：ADR-020 / ADR-024（凭证）、ADR-026（secret reference）

---

## 一、结论先行

**不需要公网 Owner mode。** 这不是「暂时不做」，而是当前架构里
根本没有那条路径 —— 见第二节的实测。

因此本任务验收里列出的 TOTP、会话表、重放窗口、撤销、恢复流程，
**一项都不需要实现**，因为它们的威胁在「服务只在回环地址上存在」这个前提下
不成立。本文记录的是：为什么不需要、什么情况下需要重新评估、
以及那些**在本地场景下依然成立**的威胁（两条）与它们的处置。

---

## 二、为什么不需要（实测，不是设计意图）

| 事实 | 怎么核实的 |
| --- | --- |
| 服务只绑 `127.0.0.1` | `index.mjs` 的 `BIND_HOST` 是常量，注释写明「刻意不允许改成 0.0.0.0」 |
| **不存在**任何发布到公网的路由 | 路由表逐条读过；没有反向代理、没有隧道、没有 webhook 出口 |
| 连接层二次校验来源地址 | 非 `127.0.0.1` / `::1` 的连接在 `createServer` 里直接 403 |
| 每个请求都要鉴权，包括 `/api/health` | 路由层在鉴权之后才分流 |
| 数据不出本机 | 唯一的出网调用是模型/嵌入端点，默认只允许本机地址（`assertEndpointAllowed`） |

关键区别在于「**默认关闭**」与「**没有那条代码路径**」。
前者靠配置正确，后者靠不存在。这个项目选的是后者 ——
因为配置会被改，而不存在的代码不会被误开。

### 任务原文与实际的一个出入

验收里写的是「TOTP」「OTP 不参与加密」。这两条针对的是
**把管理端暴露到公网**之后必须补的认证强度。
而本项目的决定是**不暴露**，所以它们不是被简化了，是前提不成立。

如果将来要公开 Owner mode，那是一次**架构变更**，不是给现有服务加个开关 ——
届时 TOTP、会话表、重放、撤销、恢复、限流要重新设计，本文的结论不适用。

## 三、本地场景下**依然成立**的两条威胁

「只绑回环」挡的是别的机器，挡不住**本机上跑着的网页**。

### 威胁 ①：DNS rebinding

外站的脚本可以把自己的域名解析到 `127.0.0.1`（`nip.io` 这类通配 DNS
天生就是干这个的），于是浏览器认为「外站与本地服务同源」，
请求就会打到本地服务上 —— 而服务端看到的 `remoteAddress` 确实是 `127.0.0.1`，
连接层的校验完全放行。

区别只剩一个地方：**`Host` 头**。浏览器发的是 `Host: evil.com`。

**处置**：`studio/server/guard.mjs` 的 `hostAllowed()`，只接受
`127.0.0.1:<port>` / `localhost:<port>` / `[::1]:<port>` 三种写法。
刻意**不接受**任何域名，哪怕它当下解析到本机 —— DNS 随时可改，
「现在指向本机」不构成它可以冒充本机的理由。

返回 **403** 而不是 401：这是地址不对，不是凭据不对。
两者的下一步动作不同，提示语混在一起会让人去反复检查令牌。

### 威胁 ②：无限次猜令牌

令牌是 32 字节随机（256 位熵），猜不中。但「猜不中」不等于「不用管」：

- 无限次尝试会把日志淹没，让真正的异常淹没在噪声里
- 将来任何一次**熵不足的改动**会直接变成可攻破，而现在没有任何东西拦住它

**处置**：`createLoginThrottle()`，滑动窗口，默认 10 次失败 / 60 秒。
设计上有三点是刻意的：

1. **只统计失败**。用户自己反复登录（换设备、清 Cookie）不该把自己锁在门外。
   成功登录会把计数清零。
2. **窗口滑动即恢复**，不需要后台任务，也不需要把锁死状态写进磁盘 ——
   后者会带来一个更难收拾的局面：程序崩在锁定期间，锁死状态却留了下来。
3. **限流器属于服务实例，不是模块级全局**。写成模块级会让同一进程里的
   两个服务共用一份计数（测试里立刻暴露了），而且无法重置。

## 四、会话与撤销：现状与取舍

会话的实现是：**Cookie 里存的就是令牌本身**，服务端不维护会话表。

这样做的收益是不需要存储、重启即失效；代价是**没有细粒度的撤销**。
现状下的撤销手段只有一条：

```
换掉 ~/.frees-studio/token → 重启服务
```

这个取舍成立的理由：本地单用户场景下，「撤销某个会话」的需求来自
「多设备登录、怀疑某一台失陷」。而本服务只有一个用户、通常只有一台机器，
真正需要撤销时的正确动作是**轮换令牌**，那本来就是一次重启的事。

需要重新评估的信号：如果将来出现「A 机器上的会话要单独踢掉、B 机器保留」
这种需求，说明会话模型该换成服务端会话表了。现在不做。

### 其余已核实成立的性质

| 性质 | 实现 |
| --- | --- |
| Cookie 不可被脚本读取 | `HttpOnly` |
| 跨站请求不携带 Cookie（免 CSRF） | `SameSite=Strict` |
| Cookie 不漏给别的 host | 不设 `Domain` |
| 关闭浏览器即失效 | 不设 `Max-Age` / `Expires`（会话 Cookie） |
| 令牌比较不泄漏时序 | `timingSafeEqual` |
| 静态文件不能越出根目录 | 归一化剥 `../` **加** `startsWith` 根校验（两层） |

`Secure` 标志**刻意不加**：服务是 `http://127.0.0.1`，加了它浏览器
根本不会回传 Cookie，等于把自己锁在外面。

## 五、验证

`studio/server/guard.test.mjs`（16 项）：

- Host 白名单：三种回环写法放行；`evil.com`、`127.0.0.1.nip.io`、
  `localhost.evil.com`、端口不符的一律拒绝
- HTTP 层：伪造 Host 得到 403（**连 `/api/health` 也不放行**）；
  正常 Host 仍可访问
- 限流：只统计失败、成功清零、窗口滑动恢复、退避时间递减、来源之间互不影响
- HTTP 层：持续猜令牌得到 429 且带 `Retry-After`；正确令牌仍能登录（不误伤）
- Cookie 属性：`HttpOnly`、`SameSite=Strict`、无 `Domain`、非持久
- 401 与 403 语义区分
- 路径穿越：12 种写法（含二次编码、反斜杠、`....//`）全部挡住，
  **同时**确认正常路径仍能读到

### 一处需要说明的验证局限

路径穿越的用例**只删掉一层防线时仍会通过** —— `resolveStatic` 里
有两层互相独立的防线（归一化剥 `../`、`startsWith` 根校验），任何一层单独
存在都足够。实测确认：把**两层一起**去掉，用例才会报出「越出了根目录」。

这不是缺陷，是纵深防御的必然结果，但它是**验证时的陷阱**：
只看「用例通过」会以为两层都在工作，实际上可能是其中一层在替另一层兜底。
说明写进了用例本身的注释里。

## 五之二、Studio 预览：一处真实的提权路径（2026-09-17 修）

自动安全审查指出 `studio/web/app.js` 里 `preview.innerHTML = html` 有 XSS 风险。
**核实后确认成立**，且它不是「自己给自己注入」那么无害：

渲染管线按设计**透传裸 HTML**（Astro 的 markdown 如此）。于是
「从网页或 AI 输出里粘一段带 `<script>` 的内容，再点预览」
就会以**当前会话的身份**执行它。

关键在于这与公开站**不等价**：公开站是静态站点，没有会话可偷；
而 Studio 的预览跑在已认证的页面上，脚本能调 `/api/notes`、`/api/memories`。
同一个渲染结果，在两处的危害差了一个量级。
项目自己也把「外部文档、网页与历史对话中的文本均视为不可信内容」
写进了 ACCESS-001 —— 这条正是那个原则在编辑器上的落点。

**修法：沙箱 iframe，不是过滤标签。**

```
<iframe id="preview" sandbox title="预览"></iframe>
```

`sandbox` 不带 `allow-scripts` 也不带 `allow-same-origin`：脚本不执行，
框架也读不到父页面、用不上会话。

为什么不用「把危险标签过滤掉」：
1. 自己写 HTML 过滤器是出了名容易漏的活（`<svg>`、`<math>`、事件处理器、
   协议绕过……），而沙箱是**浏览器保证**的
2. 过滤会让预览与发布的 HTML 不再相同，而「所见即所发」正是这个预览的
   全部意义。沙箱则**保真度不受影响**：HTML 还是同一份，只是不执行

**验证**（真实 Chrome，内容取自「外部粘贴」的形态）：

| 检查 | 结果 |
| --- | --- |
| 父页面被脚本改动 | ✅ 没有 |
| 父页面能读 iframe 文档 | ✅ 不能（OPAQUE 源） |
| srcdoc 里仍然带着 `<script>` | ✅ 是 —— 说明是沙箱挡住的，不是被过滤掉 |
| 标题/正文照常渲染、prose.css 生效 | ✅ 截图确认 |

最后一条尤其重要：**如果 srcdoc 里的 `<script>` 不见了，那说明我测的是过滤器，
而不是沙箱** —— 一个「内容被改过」的通过和一个「内容没变但执行不了」的
通过，含义完全不同。

同时核对了全部 `innerHTML` 用法：修完只剩 0 处赋值，其余渲染一律走
`textContent` / `createElement`。

## 六、什么情况下要重开这个结论

出现**任意一条**，本文的结论即失效，需要按公网服务的标准重做认证：

1. 出现把服务暴露到非回环地址的需求（反向代理、隧道、内网其他机器访问）
2. 出现多用户或多设备各自需要独立会话的场景
3. 出现从公网触发的自动化（webhook、CI 回调、远程备份触发）

在此之前，「不做公网 Owner mode」不是省事，是**唯一不会引入
未经设计的攻击面的选择**。
