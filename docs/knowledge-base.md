# 私人知识库：架构决定与实现

日期：2026-09-17
状态：架构已定，基础层实现中

---

## 一、必须先说清的硬约束

需求写的是「让用户直接通过 frees-ling.dev 保存、查阅、编辑和整理自己的知识」。

**这在当前托管方式下做不到，原因不是没设计好，而是 GitHub Pages 是纯静态托管**：

| 能力 | GitHub Pages |
| --- | --- |
| 运行服务端代码 | ❌ |
| 认证用户 | ❌ |
| 存储数据 | ❌ |
| 按用户返回不同内容 | ❌ |

要在公网上「登录后编辑」，必须有后端。而可用后端的路径都被已定的边界排除：

| 路径 | 排除理由 |
| --- | --- |
| 买服务器 / 托管后端 | 用户明确要求不为此购买新商业服务 |
| Cloudflare Workers + KV | 引入新的付费依赖与生产边界变更，需另行授权 |
| 浏览器直连 WebDAV | 违反「WebDAV 密码不得进入浏览器存储」 |
| 浏览器端加密后存公开仓库 | 密钥管理无安全落点；轮换与丢失恢复都无解 |

**因此唯一自洽的形态是本地优先**（这也是 ADR-002 已经定下的方向）：

> 知识库运行在**你自己的机器**上，通过 `localhost` 访问，数据存在本地。
> `frees-ling.dev` 只承载**你显式发布**的内容 —— 它永远拿不到私人数据。

这不是妥协，而是把「私人」真正做实：私人数据从不离开本机，
比「公网服务器上加了密码」更安全。

## 二、三层数据模型（对应需求第四节的区分）

| 层 | 是什么 | 谁写的 | 可否被 AI 读 | 是否可能公开 |
| --- | --- | --- | --- | --- |
| **原始档案** | 完整历史：对话原文、导入的文档、修改记录 | 导入 / 自动记录 | 需显式授权 | 否 |
| **长期记忆** | 从档案中提取、**经人工确认**的偏好与决策 | AI 提取 + **人工审核** | 是（默认） | 否 |
| **知识库** | 正式整理的笔记与文章 | 人 | 是 | **仅显式发布的部分** |

**不可逾越的规则**：AI 自动总结**不得**直接成为「已验证事实」。
提取出的记忆一律先进入待审核状态，带来源与置信度，人工确认后才升格。

## 三、技术选型（零新依赖）

| 需求 | 方案 | 理由 |
| --- | --- | --- |
| 存储 | **`node:sqlite`** | Node 26 内置，已实测可用（含 WAL）。不引入 better-sqlite3 等原生模块，避免编译与跨平台问题 |
| 迁移 | 自己写 `schema_version` 表 + 顺序迁移 | 需求只要「可靠、可回滚」，ORM 带来的复杂度大于收益 |
| 本地服务 | Node 内置 `node:http` | 不引入 Express/Fastify。接口数量少，内置足够 |
| 前端 | 现有 Astro 组件 + 原生 JS | 复用书房的视觉语言与 tokens，不引入第二个前端栈 |
| 全文检索 | SQLite FTS5 | 内置，与数据同库同事务，避免「索引与数据不一致」 |
| 绑定 | **仅 `127.0.0.1`** | 不监听 `0.0.0.0`，局域网也访问不到 |

**已实测**：`node:sqlite` 的 `DatabaseSync` 可建表、写入、读取，`PRAGMA journal_mode=WAL` 生效。

## 四、访问控制

本地服务同样需要认证 —— 本机上任何进程都能访问 `localhost`。

- 首次启动生成随机 token，写入 `~/.frees-studio/token`（权限 `600`）
- 所有请求校验 `Authorization` 头
- 服务只绑 `127.0.0.1`；**不提供任何对公网开放的开关**
- 不做「默认密码」，没有密码就是没有账户

**明确不做**：不实现公网 Owner mode。需求里提到过，但那需要后端与 TOTP，
属于 SEC-002 的范畴，且有「是否真的需要」这一前置问题未答。

## 五、数据位置

```
~/.frees-studio/
  studio.db          # SQLite 主库（含 WAL 与 shm）
  token              # 本地访问令牌，600
  media/             # 附件
  backups/           # 快照
```

**放在用户主目录而不是仓库内**，理由是仓库会被 `git add -A` 扫描，
把私人数据库放进工作区等于给「误提交」留机会。`check-secrets.mjs` 也会拦
`.db` 路径 —— 与其依赖拦截，不如一开始就不放进去。

## 七、与现有博客的关系

- **不重写博客**。知识库是新增的一层，公开站保持现状
- 复用：`prose.css` 的阅读样式、`tokens.css` 的设计变量、`relations.ts` 的关联算法
- 发布路径：知识库 → 导出 → `src/content/posts/*.md` → 现有构建流程
  （即公开站完全不感知知识库的存在，它只看到普通的 Markdown 文件）
