## 一、实测结构（推翻 RENDER-001 的两处结论）

RENDER-001 说「h2 = 543，transformer 是结构上不同的文档」。方向对，数字不对。
重新按**产出 HTML**清点（不是按源码 `grep '^# '`）：

| 项 | RENDER-001 | 本次实测 |
| --- | --- | --- |
| `h1` | 未统计 | **109** |
| `h2` | 543 | **471** |
| `h3` | 未统计 | **71** |
| 标题总数 | — | **651** |
| 有 `id` 的标题 | — | **651（全部）** |

RENDER-001 的 543 是用 `grep -c '^## '` 数源码得到的，而**这个数法本身是错的**：

```python
# transformer.md 里真实存在的一行
# 输出: [1 2] → [2 2]      ← 这是代码块里的 Python 注释，不是标题
```

用 `grep '^# '` 数出 **437 个 h1**，但其中绝大多数是 fenced code block 里的
Python / shell 注释。**只有渲染出来的 HTML 才是可核验的事实**：
109 个 h1，而且 `id` 一个都不少（`id="前言"`、`id="第一层什么叫空间"`…）。

### 这篇文章的真正形状

- **109 个顶级章节**（h1），每章平均 4.3 个 h2（最少 1，最多 14，**没有空章节**）
- 全文约 148,691 字符（去代码块计），产出正文 HTML 1.11 MB
- 章节自带阶段结构，但**标记不完整**：有「第二阶段」到「第七阶段」，
  **没有「第一阶段」** —— 开头那 22 课没有归入任何阶段

### 内容侧的既有问题（本次只记录，不代用户决定）

1. **课号重复与乱序**：`第 66 课`、`第 67 课`、`第 68 课` 各出现两次；
   `第 80 课` 夹在 71–76 之间；`第 64 课` 排在 `第 68 课` 之后。
   这是**内容**问题，不是渲染问题。渲染器不得替它重新编号 ——
   锚点一旦按课号生成，重号就会互相覆盖。
2. **546 个 `hr`** 当分隔线用。渲染器不该替内容做这个决定，
   但它是正文 HTML 里最大的一块结构性开销。

## 二、分章方案：**页内分章**，不拆 URL

### 被否决的方案：拆成枢纽页 + 章节页

即 `/blog/transformer/` 作目录、`/blog/transformer/<章节>/` 各自成页。它的问题
不是「工作量大」，而是三条**无法在本项目里解决**的硬约束：

1. **用户的既有决定**：导航重设计时已明确「保留现有 URL —— 文章 URL 完全不动」。
   新增 109 个 URL 与这条冲突。
2. **GitHub Pages 不支持服务端重定向**。拆完之后，指向
   `/blog/transformer/#第一层什么叫空间` 的旧链接**全部落空**，而这篇文章有
   651 个锚点。枢纽页可以给每个章节条目挂上旧 id，让旧链接落到目录条目上 ——
   但那已经是**降级**：用户点进去看到的不再是内容，是目录里的一个链接。
3. **SEO 摊薄**：一个 1.38 MB 的页面确实不利于抓取，但拆成 109 个薄页会把
   现有的搜索权重摊开，而每页都要重复整套导航。

### 采用：页内分章

在同一 URL 内解决**导航与结构**问题，不动 URL、不动锚点：

| 要修的 | 怎么修 |
| --- | --- |
| 650 项的平铺目录 | 按 109 个顶级章节做**两级目录**，默认只展开当前章 |
| 110 个 `h1`（页面标题 + 109 个正文 h1） | 正文标题**整体降一级**（渲染期做，不改 `.md`） |
| 长文无位置感 | 目录高亮当前章（缓存标题偏移 + 滚动时二分，每帧不读 rect） |

**标题降级在渲染期做，不改任何 `.md`。** 理由：`.md` 是用户的写作，
而「正文 `#` 应该是页面的 h2」是**渲染器的判断**，不该回写到内容里。
放在渲染期还带来两个好处：一次改动全站 17 篇一起受益（每篇都有正文 h1），
以及随时可以撤掉。

**锚点稳定性**：`id` 由标题**文本**生成，与层级无关，因此降级不改变任何 id。
651 个锚点全部保持不变 —— 这一点由 `npm run check:coverage` 强制。

**这一方案不解决的问题**：页面重量。1.38 MB 的 HTML 依旧是 1.38 MB。
那是 `PERF-001` 的范围（Shiki 行内样式改成类名、`hr` 的渲染开销），
本条不越界去动。

## 四、迁移脚本与回滚

分章**不需要**数据迁移：不移动内容、不改文件、不改 URL。
它是一次渲染期变换，回滚 = 撤掉那个 rehype 插件。

真正需要工具的是**证明没有丢东西**，因此本任务交付的是闸门而非迁移脚本：

```
npm run check:coverage           # 与基线比对
npm run check:coverage -- --write  # 确认无误后更新基线
```

基线：`docs/execution/content-manifest.json`，逐篇记录
**① 标题 ② 正文纯文本 sha256 ③ 锚点 id 集合哈希 ④ 各级标题计数**。

### 这道闸门在本次开发中被实测证伪过两次

两条都是**会说谎**的缺陷，记在这里，因为它们比闸门本身更容易再次发生：

1. **范围取错 → 报错报到别的文章头上。**
   最初写成「从 `.prose` 切到 `</article>`」，把上下篇导航、许可声明、
   评论一并算了进去。实测：只改 `thinking.md` 的 frontmatter 标题，
   闸门报的是 **`shadowrocket` 正文变化** —— 因为 thinking 的标题变了，
   shadowrocket 的「上一篇」链接跟着变。修法：按 `<div>` 配对精确取区，
   并加一条断言（正文区里出现 `post-nav` / `see-also` / `comments` 就报错退出）。

2. **在陈旧产物上写基线。**
   闸门读的是 `dist/`，而 `dist` 可能比 `src` 旧。实测：改完源文件、建过一次、
   再改回来，此时 `dist` 里还是中间态，`--write` 就把那个从未存在过的状态
   记成了基线。修法：写基线前比较 `src/` 与 `dist/` 的最新 mtime，
   `dist` 更旧就拒绝运行。

两道防线都有对应的失败复现步骤，见上面两段。

### 实施后补记（RENDER-003）

落地时被实测推翻的三处判断，写在这里因为它们都属于「想当然」：

1. **用 IntersectionObserver 的窄带判断当前章不可靠。** 锚点跳转的落点是
   `scroll-margin-top: 76px`，恰好落在带外 —— 点目录跳过去之后目录不跟随，
   而这正是本功能的核心场景。改为缓存标题文档偏移 + 滚动时二分查找。
2. **`<a>` 放进 `<summary>` 是嵌套交互控件**（axe `nested-interactive` ×109）。
   `<summary>` 本身有 button 语义，里面不能再放链接。
3. **程序改 `open` 同样派发 `toggle` 事件**，于是「用户手动展开过」的标志
   会被自己的自动展开误置，导致「只展开当前章」永久失效。

另外，侧栏内滚动**不能用 `scrollIntoView`**：它会滚动所有可滚动祖先，
包括文档本身，于是正文的阅读位置会被侧栏带着跳。直接改 `scrollTop`。
