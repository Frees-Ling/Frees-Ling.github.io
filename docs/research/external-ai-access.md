# 外部 AI 访问本地知识库：可行性核实（ACCESS-001）

- **Checked on**：2026-09-17
- **Official source**：OpenAI 开发者模式与 MCP apps 文档
  <https://developers.openai.com/api/docs/guides/developer-mode.md>
  （检索时官方文档地址；菜单名称 OpenAI 已多次改名，connectors → apps → plugins）
- **Tested version/account tier**：**未实测**。需要付费账号（Plus/Pro/Business/
  Enterprise/Education 之一）与公网 HTTPS 端点，两者都没有。
  因此本文只记录**官方文档明确写出的**约束，不推断。

---

## 一、结论先行

**「仅凭 API Key 就能让 ChatGPT 访问本地知识库」是错的。** 三个环节都不成立：

1. **ChatGPT 不接受粘贴 API Key 作为 MCP 连接器的认证方式。**
   它支持的是 OAuth（含 DCR/CIMD）、无认证、以及混合模式 ——
   没有「贴一个 API key」这一档。
2. **服务必须在公网 HTTPS 上可达。** 官方明确：VPN / 私网的服务器连不上，
   本地开发要用隧道（ngrok、Cloudflare Tunnel 等）。
3. **需要付费套餐 + 开发者模式。** 免费版没有；Business/Enterprise/Edu
   还要管理员先开权限。

本项目的服务**只绑回环地址**（`BIND_HOST` 是常量，注释写明刻意不允许改成
`0.0.0.0`），因此**现状下外部 AI 无法直接访问它** —— 这不是配置问题，
是没有那条路径（见 SEC-002）。

---

## 二、官方文档确认的能力（原文要点）

| 项 | 内容 |
| --- | --- |
| 连接方式 | 远程 MCP（SSE / Streamable HTTP），注册为 ChatGPT 里的「app」 |
| 可达性 | **必须公网 HTTPS**；私网/VPN 不可达，本地开发需隧道 |
| 认证 | OAuth（静态凭据 / CIMD / DCR / `private_key_jwt`）、无认证、混合 |
| 已知坑 | `client_secret_post` 令牌端点认证会失败，要用 `client_secret_basic` |
| 套餐 | Plus / Pro / Business / Enterprise / Education；免费版不可用 |
| 管理 | Business/Enterprise/Edu 需管理员先开开发者模式 |
| 启用 | 连接器**不会自动生效**，要在每次对话里手动选（最常见的「坏了」原因） |
| 写操作 | 每次调用默认需人工确认（除非在本对话里批准过） |
| 安全提示 | 官方明确：自定义连接器**未经 OpenAI 验证**；提醒注意提示词注入、
  误操作破坏数据、恶意 MCP 服务器窃取信息 |

最后一条与本项目 ACCESS-001 里那句「外部文档、网页与历史对话中的文本均视为
不可信内容」是同一个担忧，只是方向相反：那边担心的是**外部内容**污染本地，
这边担心的是**外部 AI** 越权操作本地。

## 三、因此哪些能做、哪些不能

### 不能（记为后续集成任务，不假装已具备）

- **让 ChatGPT 直接连本机**。需要用户自己决定开一条隧道，把服务暴露到公网。
  那是**架构变更**，不是给现有服务加个开关：SEC-002 的整套威胁模型
  （令牌、Host 校验、限流、会话）都是在「只绑回环」这个前提下成立的。
- **MCP 服务器实现**。要写 SSE/Streamable HTTP 传输、OAuth 授权服务器、
  工具清单与 schema。这是一整个子系统，不是本次能做完的。
- **无认证模式**。官方支持，但对本项目的私人内容而言等于把知识库公开 ——
  明确不采用。

### 能做，且本次已做（这是本次真正的交付）

**受限访问身份**：即使将来真的开了隧道，也不该把主令牌交出去。
主令牌是全权的 —— 拿到它就能读全部私人笔记、记忆、对话历史，
还能发起对话（等于把私人内容送到模型端点）。

`studio/access/tokens.mjs` 把它拆成具名、有范围、可撤销、可审计的身份：

| 预设 | 能力 | 用途 |
| --- | --- | --- |
| `searcher` | `read:search` | 只搜，读不到全文 —— 最保守的一档 |
| `reader` | `read:search` `read:notes` `read:memories` | 只读的检索伙伴 |
| `drafter` | 上述 + `write:draft` | 能提草稿，但不能让草稿生效 |

三条设计规则：

1. **默认拒绝**。scopes 为空则什么都不能做；**未分类的路径一律要求 `admin`**。
   将来加了新路由却忘了分类，结果是「够不着」而不是「默认放行」。
2. **只存哈希**（同 ADR-026）。明文只在创建那一刻返回一次。
3. **审计记「谁访问了什么」，不记内容** —— 一份用来防泄漏的日志
   自己不该成为泄漏面。

### 还有一条做不到的，要说清楚

官方文档说 MCP 服务器的工具清单由**连接时读取一次**并缓存。
这意味着「改了权限之后 ChatGPT 那边不会自动知道」——
权限变更必须在 ChatGPT 侧重新连接才生效。这是平台行为，不是本项目的选择。

## 四、本次实测中发现的两个真问题

都是自己写的用例抓到的，记在这里因为它们都属于「看起来对」的那一类：

1. **`DELETE /api/notes/:id` 被算成了 `write:draft`。** 我原先只按
   「GET 还是非 GET」二分，于是**一个「可以提草稿」的身份能删掉任何一篇笔记**。
   删除是对已存在内容的破坏性操作，与「提一条草稿等人审」是两回事。
   现在只有 `POST /api/notes`（新建）算 `write:draft`，改与删都要 `admin`。
2. **受限身份的写入没有被标记成 `ai_draft`。** 能力检查只回答「这个身份
   能不能碰这个端点」，不回答「它写出来的东西算谁的」。于是外部 AI 写的内容
   会以 `origin: 'human'` 进入，与用户亲手写的无法区分 ——
   而「AI 自动总结不得直接当作已验证事实」正是三层模型的基石。
   现在受限身份的写入一律记为 `ai_draft`。

## 五、未决与后续集成任务

- **MCP 服务器 + OAuth 授权服务器**：一整个子系统，需要真实公网端点才能验证。
- **隧道的安全边界**：若用户决定开隧道，需要重新评估 SEC-002 的威胁模型，
  并至少加上：按身份的请求频率上限、来源 IP 之外的额外校验、
  以及「隧道关掉时数据不出本机」的确认。**在那之前不做**。
- **连接器侧的权限同步**：如第三节末尾所述，是平台行为，需要文档告知用户。
- **本地模型路径**：本文只核实了 ChatGPT。若改用本机模型（LM Studio），
  不存在公网可达问题 —— 但那已经是另一条路径，不在本任务范围。
