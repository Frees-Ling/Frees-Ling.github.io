## 一、必须先分清：这是两套不同的接口

官方文档里只有一套接口，而它**不是** WebDAV。

| | OpenAPI | WebDAV |
| --- | --- | --- |
| 协议 | JSON over HTTPS（REST） | WebDAV（RFC 4918） |
| 域名 | `https://open-api.123pan.com` | 形如 `http://webdav-xxx.pd1.123pan.cn/webdav`，地址在会员中心的「第三方挂载」页生成 |
| 鉴权 | `Authorization: Bearer <access_token>` + **必填**头 `Platform: open_platform` + `Content-Type: application/json` | HTTP Basic，账号为注册手机号，密码是页面生成的**专用密码**（不是登录密码） |
| 凭据形态 | `client_id` / `client_secret` 换 access_token | 专用应用密码 |
| 有效期 | token **30 天**；同一 `client_id` 同时最多 **3 个** token，重复颁发会把旧的顶下线 | 文档未说明 |
| 计费 | 购买开发者权益包即可开通，「无需等待审核」 | WebDAV 是**会员功能**（VIP/SVIP） |
| 官方文档 | **有**，含逐接口 QPS 上限 | **无** —— 官方 API 文档中「WebDAV」一词零次出现 |

来源为上述两个官方页面。总览页原文自称
「当前平台文档处于持续更新与完善阶段」，因此本文只记录**本次抓到的内容**，
不推断后续。

## 二、对本项目的直接影响

备份传输层（KB-011）实现的是 **WebDAV**。而按第一节：

1. **官方从未承诺 WebDAV 的协议细节。** PROPFIND 的 depth 语义、href 形态、
   Range 支持、错误码、路径规范化规则 —— 一条都没有官方说明。
   这意味着我们客户端里那些「按 RFC 4918 写的」假设，
   **在这家服务上没有任何书面保证**。
2. **限额未知。** OpenAPI 逐个接口标了 QPS，WebDAV 没有任何说明。
   我们的保留策略会 `PROPFIND` + 若干 `DELETE`，
   在未知限额下**没有任何退避依据**。
3. **计费门槛不同。** OpenAPI 要开发者权益包，WebDAV 要会员。两者不是一回事。

### 已核实的缓解事实

备份编排 `runBackup` / `runRetention` 只调用四个方法
（`put` / `get` / `list` / `del`，见 `studio/backup/remote.mjs`），
**不认识 WebDAV 这个词**。因此：

- 换传输协议的代价 = 新写一个实现同样四个方法的适配器，
  **编排、加密、回读校验、保留策略都不用动**
- 这一点是**结构上可核验的**，不是承诺：`remote.mjs` 里对
  `webdav` 的调用一共四处，全是这四个方法

因此结论不是「WebDAV 不能用」，而是：**不要让自己只能走 WebDAV**。

## 三、OpenAPI 已确认的能力（供将来选型）

- 文件操作：上传（目录、文件）、删除、重命名、移动、查看详情、获取列表
- **「支持大文件断点续传与并行上传」**（原文）
- 直链：定位为「基于CDN内容分发网络的文件下载服务」，无带宽/有效期说明
- 图床、视频转码（转 M3U8）属另一组接口
- 成功判定：`code == 0`；`401` = access_token 无效；`429` = 请求太频繁
- 排障需要 `x-traceID`

**已确认的 QPS 上限**（原文逐条列出，单位均为 QPS）：

| 接口 | QPS |
| --- | --- |
| `api/v2/file/list` | 15 |
| `api/v1/file/list` | 10 |
| `api/v1/file/delete` | 10 |
| `api/v1/file/move` | 20 |
| `upload/v1/file/mkdir` | 20 |
| `api/v1/access_token` | 10 |
| `api/v1/user/info` | 10 |

对我们的备份频率（每天几次）而言这些上限绰绰有余；
有意义的是它们**存在且被写明** —— 这正好是 WebDAV 缺的那一块。

## 四、受控测试：我方客户端的解析规则

没有 123 云盘凭据，因此这一节测的**不是** 123 云盘，
而是「我们客户端自身的假设在真实 WebDAV 服务端上是否成立」。
服务端用 wsgidav 4.3.5（一个真实实现，不是我们的 mock）。

### 抓到的第二个缺陷：列举结果可被用来越界删除（已修）

自动安全审查指出 `list()` 的路径检查不足，**核实后确认可利用**：

`%2F` 在 URL 解析阶段**不是**路径分隔符（规范如此），因此
`/backups/..%2Fevil` 解析出来仍带着字面量，直到 `decodeURIComponent`
之后才变成 `/backups/../evil` —— 它**通过了** `startsWith(dirPrefix)` 检查，
切出来是 `../evil`。保留策略据此构造 `/backups/../evil`，
被 HTTP 客户端规范化成 `/evil`，**删到备份目录外面**。

实测确认的越界向量：

```
/backups/..%2Fevil
/backups/%2E%2E%2Fevil          → 名称 "../evil" → DELETE /evil
/backups/frees-studio-..%2F..%2Fevil   （还能通过保留策略的前缀过滤）
```

**两道防线**（各自独立）：

1. `list()` 只返回**单个文件名** —— 含分隔符或点号段的项直接丢弃。
   深度 1 的 PROPFIND 本来就不该返回带分隔符的项。
   **丢弃而非放行**：丢掉的代价是「少看到一个文件」，放行的代价是
   「删错文件」，两者不对等。
2. `url()` 逐段拒绝 `.` 与 `..`，即使第一道漏了也不会真的发出去。

一个教训写进用例注释：原先有一条用例**把这个危险形态断言成了预期行为**
（「嵌套项会带上相对路径一起返回」）。一个把缺陷固定下来的测试比没有测试
更糟 —— 它会让后来的人以为那是设计意图。

### 抓到的第一个缺陷（已修）

`list()` 原先**先解码 href、再交给 `new URL()`**。顺序反了就出两种错：

```
/backups/hash%231.freesbk   → 解码 → /backups/hash#1.freesbk
                            → new URL().pathname → /backups/hash      ← # 之后没了
/backups/q%3Fmark.freesbk   → 解码 → /backups/q?mark.freesbk
                            → new URL().pathname → /backups/q          ← ? 之后没了
```

实测输出：`hash#1.freesbk` 与 `q?mark.freesbk` 分别被列举成 `hash` 与 `q`。
同时 `with%20space` 反被 `new URL()` 重新编码回 `with%20space`（漏解码）。

**为什么这在备份场景里会出事**：保留策略按名字删除。两个文件
`a#1` / `a#2` 会双双报成 `a` —— 要么删错，要么删不掉，
而两者都不报错。这与 KB-011 里那个「href 只认完整 URL」是同一类问题：
**列举结果不准，而下游把它当事实用**。

修法：**先把 href 解析成路径，再解码**。
非法百分号序列不能让整次列举失败（否则会被保留策略解读成「没有备份」）。

### 覆盖到的路径形态（全部通过）

| 形态 | put / get / 回读 / 列举 |
| --- | --- |
| 纯 ASCII | ✅ |
| 中文文件名 | ✅ |
| 中文目录（嵌套） | ✅ |
| 空格 | ✅ |
| `#` | ✅ |
| `?` | ✅ |
| `%` | ✅ |
| `+` | ✅ |
| `&` | ✅ |
| emoji | ✅ |

回归用例见 `studio/backup/webdav.test.mjs`（10 项，不连服务器，
喂构造好的 PROPFIND 响应）。**敏感性已验证**：把「先解析再解码」
改回错误顺序，恰好那两条相关用例失败，其余全过。

## 五、已知限制与未知项

**已知**：

- 我方客户端**不使用 Range**（每次整取），因此 Range 支持与否不影响当前实现；
  将来若做增量备份则会依赖它 —— 而 WebDAV 侧没有官方说明
- 不带「分片 / 直传」能力。备份体积在 KB 级，用不到；
  真要传大文件时应走 OpenAPI 的断点续传
- 我方客户端**不自动创建远端目录**（`MKCOL`），目录不存在时明确报错

**未知（需要凭据才能回答）**：

- 123 云盘 WebDAV 的 PROPFIND depth 语义、href 形态（绝对路径还是完整 URL）
- 是否有 QPS / 并发限制，超限返回什么
- 路径规范化规则：大小写敏感性、非 ASCII 归一化（NFC/NFD）、
  尾随空格与点、保留字符
- 专用密码的权限范围：是否只能访问某个目录、能否越出
- 三个 endpoint（Public / Collection / Security）能否由独立凭据可靠隔离
- 免费额度与会员过期后已上传数据的可访问性

## 六、安全影响

1. **WebDAV 用 HTTP Basic，凭据在每次请求里明文传输**（依赖 TLS 保护）。
   这与 OpenAPI 的 Bearer token 是两种不同的暴露面：
   Basic 密码一旦泄漏就是长期的，且不能像 token 那样靠 30 天有效期收窄窗口。
   因此 WebDAV 密码必须走 secret reference（ADR-026），
   绝不落库、不进日志 —— 这一点已经做到。
2. **专用密码的权限边界未知**。若它实际能访问整个网盘，
   那么「三个 endpoint 最小权限隔离」这个架构设想**在 WebDAV 上可能不成立**，
   需要改用 OpenAPI 的独立 `client_id`。
   这是**尚未验证的架构前提**，不是已知事实。
3. 备份本身是加密的（KB-010，AES-256-GCM + scrypt），
   因此即使远端被读取，内容也不可解 —— 这是当前设计里最重要的一条缓冲。

---

## 七、结论与建议

1. **不要在没有凭据的情况下假定 WebDAV 可用**。它是会员功能、没有官方协议文档、
   限额未知。
2. **保持传输层可替换**。编排只依赖四个方法，已满足；
   但**尚未有第二个实现**，因此「可替换」还没有被验证过 ——
   建议在拿到凭据之前，先补一个 OpenAPI 适配器的最小骨架（实现同样四个方法，
   用 stub 测试），让「可替换」从结构事实变成被测试过的事实。
3. **拿到凭据后要按第五节的未知项逐条实测**，并把结果补进本文档。
   在那之前，第五节列出的每一条都是**风险**而不是背景信息。
